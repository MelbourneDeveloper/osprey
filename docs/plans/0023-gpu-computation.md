# Plan 0023 — GPU Computation: Surface Completion & Device Backends

**Subsystem:** `crates/osprey-types` + `crates/osprey-codegen` + `compiler/runtime` (+ CLI target drivers) **Status:** **General device execution shipped (2026-10-15): every extracted kernel is compiled to the shared device dialect and runs on Metal or OpenCL, and GPT-2 inference and training run every kernel and every product on the device.** Stages 1–2 (typed surface, purity checking, CPU host backend, eleven built-ins, differential corpus) are complete. Stage 3 (kernel extraction, `[GPU-KERNEL-EXTRACT]`) has landed for admissible inline/let-bound lambda and scalar builtin kernels, with two shapes that still decline, listed under the stage 3 checklist. Stage 4 has the shared dispatch contract, two adapters, a binary64 library with correctly rounded `exp`/`ln`/`tanh`, and an AST-to-dialect emitter for `gpuMap`/`gpuZipWith`/`gpuFold` kernels (`crates/osprey-codegen/src/gpu_device.rs`); `gpuScan` and `gpuFilter` have no device form yet, buffers are not device-resident, and the 2× performance gates remain open. Stage 5 landed as the program's own `Tensor<B>` effect. **The reference application runs on both paths (2026-10-15): `examples/gpt2` generates and trains with every kernel on the GPU under `GPU=metal`/`opencl`, on the CPU under `GPU=host`, and over plain lists under `BACKEND=lists`, from one model source.** **Spec:** [0034-GPUComputation.md](../specs/0034-GPUComputation.md) **Sibling plan:** [0025 — GPU graphics backends](0025-gpu-graphics-backends.md) is **subordinate to this plan**: the graphics examples exist to demonstrate capability, and work there is admissible only where it advances `gpu*` reaching a device (the stage 6 convergence point). **Research last re-verified against primary sources:** 2026-10-12.

## Summary

**Architecture requirement (2026-10-12): Osprey is a vendor-neutral alternative to CUDA.** GPU computation must use Apple, AMD, Intel, NVIDIA, and other compute-capable GPUs directly through platform adapters, with unchanged Osprey source. CUDA libraries and interoperability remain optional capabilities; the core GPU compiler, runtime, and acceptance gates must also work without CUDA. [GPU-BACKEND-PORTABILITY](../specs/0034-GPUComputation.md#vendor-independence--gpu-backend-portability) is the authoritative contract. The earlier NVPTX-first work order is superseded.

The GPU surface is a language feature, not a library: `GpuBuffer<T>` in the type system, kernel purity proven by the effect checker (fail-closed), and a host execution backend whose fused loops over dense unboxed buffers define the reference semantics device backends must reproduce byte-for-byte. Kernel extraction makes each admissible kernel a real, first-order, capture-free function — the artifact a device emitter consumes. What remains is everything between an extracted kernel and a running device: an IR emitter, a launch and transfer path, effect-selected execution, portability backends, and the differentiation features (autodiff, schedules) the roadmap ends at.

## The ambition, stated as engineering

Osprey intends to be the language the next generation of AI and gaming infrastructure is built on — the premium language for GPU integration: one idiom from host to device, elegant on the page, safe by construction, with nothing bolted on. CUDA is a device code generator, an explicit memory hierarchy, a multi-dimensional index space, and a launch API — and Osprey today has **none of the four**. It has the thing that comes before them: a kernel that is provably pure, typed from its buffer, and compiled as a first-order function with no environment. That is real progress and roughly one quarter of the distance to a first device execution, not to parity. Every claim in this plan is held to that arithmetic.

```mermaid
flowchart TB
    A[Pure typed kernel] --> B[Extracted flat ABI]
    B --> C[Device IR emitter]
    C --> D[Launch and transfer]
    D --> E[Index spaces]
    E --> F[Memory hierarchy]
    F --> G[Schedules and autodiff]
```

## Read this first: every kernel reaches the GPU; buffers still live on the host

Every kernel [GPU-KERNEL-EXTRACT] lifts also has a device form ([GPU-BACKEND-DEVICE]): the emitter lowers the kernel's AST to the device dialect shared by `compiler/runtime/gpu_f64.metal`, `gpu_math64.metal` and `gpu_device_lib.metal`, the program's kernels travel as one string constant, and every launch site asks the runtime to run the kernel on the selected device before it runs the host loop. `gpuMap`/`gpuZipWith` run one thread per element, `gpuFold` one thread in element order, and `gpuMatMul` goes through the same dispatch. A kernel the dialect cannot express — one capturing a string, a list or a record, a `fold` over anything but a `range`, a `match` over anything but a boolean or a `gpuGet` result — declines with its reason, and a selected device aborts the run naming it rather than silently running it on the CPU. A fallible integer operation or a division by zero on the device records a fault the runtime aborts on ([GPU-DEVICE-FAULT]), because a kernel cannot reach a runtime `Arith` policy.

`make gpt2` and `make gpt2-train` run the `onGpu` handler (`BACKEND=gpu`) with `GPU=auto` by default: 22 launch sites in generation and 40 in training, zero declines, after three model kernels were rewritten so their captures are buffers and scalars rather than a record or a list (`embedRow`, `idTensor`), and the two host loops left in the samplers became kernels: the next token's index is the `Tensor` effect's `indexOf`, and the training loss is a `build` summed by `reduce`. `GPU=host` runs the same program on the CPU and `BACKEND=lists` over plain lists. What stays on the host: tokenization, `gpuIota`/`toGpu`/`fromGpu`/the loaders, and the transfer of every buffer into and out of each launch — there are no device-resident buffers and no kernel fusion, so a transformer block still moves every intermediate buffer through host memory. `gpuScan` and `gpuFilter` decline as a whole. The float library's `exp`, `ln` and `tanh` are correctly rounded (128-bit fixed point, rounded once); Apple's libm is not on every argument, so a value that passes through one can differ from the host in its last digit, as the training loss does (`4.503189215447316` host, `4.503189215447317` Metal). The four operations, `sqrt`, the conversions and the comparisons are bit-exact.

### Device evidence — 2026-10-15, Apple M4 Max, macOS arm64

- `make _test_gpu_device` and `OSPREY_GPU=opencl make _test_gpu_device`: 6 738 host/device word comparisons over five products, a compiled kernel calling `tanh64`, `exp64` and `ln64` with a scalar and a buffer uniform, a sequential reduction seeded from the host, and a faulting kernel whose fault word the runtime reads back; eight completed Metal dispatches.
- `gpu_shader_tests` compiles the three shader sources as host C: 12 000 648 checks; add, sub, mul, div, sqrt, the conversions and the comparisons agree with the host's IEEE results bit for bit over random words, subnormals and specials; `exp` agrees with Apple's libm on 798 501 of 800 000 arguments, `ln` on 799 994, `tanh` on 799 413, never further than one ulp, and every sampled disagreement was the device's correctly rounded value (checked against an 80-digit reference).
- `make gpt2 TOKENS=5`: identical text on `GPU=host` (7.4 s), `GPU=metal` (6.1 s) and `GPU=opencl` (10.5 s). `make gpt2-train`: `GPU=host` 19.4 s, `GPU=metal` 68.5 s, losses agreeing to fifteen digits. Whole-program wall clock including loading and transfers; not a native-GPU comparison and not the 2× gate.

A Metal device must not be used across `fork`, so the fault abort is covered by the mock selection suite and the hardware lane reads the fault word instead.

### The graphics bridge already exists — and is a different, subordinate plan

`examples/graphics/` is an Osprey → GPU bridge that deliberately **bypasses `gpu*`**, because `gpu*` cannot reach the GPU. The Metal path has been observed running on macOS (the 103 fps row above); the Direct3D 12 path is written but has never been compiled, linked or run on Windows (plan 0025 owns that status). Neither runs in CI: they need a display and are not in the differential corpus. The uniform-slot protocol both bridges implement is declared once, in `examples/graphics/ospgfx_abi.h`, and a kernel's leading uniform parameters are exactly a slot vector — that header is the seam stage 6 attaches to. Everything else about graphics is [plan 0025](0025-gpu-graphics-backends.md)'s, and under the current priority that plan does only what feeds stage 6.

## What works today

- `GpuBuffer<T>` with the scalar element restriction `[GPU-BUFFER-ELEM]` enforced at call sites (`builtin_constraints.rs`) and backstopped in codegen by **one predicate**, `gpu::is_scalar` (`crates/osprey-codegen/src/gpu.rs`), which element stores, kernel results, reduction accumulators, builtin-kernel slots and extracted-kernel uniforms all consult. The `Gpu#<lltype>` owner-tag scheme propagates element `LType`s through lets, pipes, parameters and returns; every tag is joined to its spelling at one point (`gpu::owner_of`).
- Eleven built-ins: `toGpu`, `fromGpu`, `gpuLength`, `gpuMap`, `gpuFold`, `gpuZipWith`, `gpuIota`, `gpuGet`, `gpuScan`, `gpuFilter`, `gpuDevice` — each with a docs entry (parity-tested) and spec ID. `toFloat` (`[BUILTIN-TOFLOAT]`) is the scalar conversion that makes float pipelines expressible. Codegen is split by role: `gpu/buffer.rs` holds the host↔buffer boundary (`toGpu` in its literal, fused and list lowerings; `fromGpu`), `gpu.rs` the combinators on a shared chassis (`map_into` for `gpuMap`/`gpuZipWith`, `reduction` for `gpuFold`/`gpuScan`, `kernel_loop` under all of them), `gpu_kernel.rs` extraction.
- Two list-free buffer constructions: buffer literals `[GPU-BUFFER-LITERAL]` and iterator fusion `[GPU-BUFFER-FUSE]`. Both emit zero `osprey_list_*` calls, pinned by `gpu_literals_make_one_buffer_with_constant_stores` and `gpu_iterator_pipelines_do_not_materialize_intermediate_collections`.
- Kernel purity `[GPU-KERNEL-PURE]` via the static effect discharge machinery (`effect_rows/gpu.rs::gpu_kernel_verdict`), fail-closed, with rejection fixtures in `examples/failscompilation/`. `Arith` is the one effect a kernel may still require on the host backend: it dispatches to the enclosing policy like any lambda's arithmetic does (spec `[GPU-KERNEL-EXTRACT]`).
- Dense-buffer C runtime (`compiler/runtime/gpu_runtime.c`) working under all three memory backends and wasm32; one bounds predicate (`addressable`) behind read, write and the `Result` gate; ARC reclaims buffers with zero leaks; 4 180 assertions in `gpu_runtime_tests.c`.
- Kernel extraction `[GPU-KERNEL-EXTRACT]` (`crates/osprey-codegen/src/gpu_kernel.rs`): an admissible kernel is lifted to a module-scope `@__gpu_kernel_N` with a flat scalar signature — captures become **leading uniform parameters**, ordered by identifier, no environment pointer, no closure cell — and the host loop calls it per element. Scalar builtins passed by name get a wrapper over their intrinsic lowering (`gpu_kernel/builtin.rs`). Per-suite extracted-definition floors are asserted for both flavors in `crates/osprey-cli/tests/cross_flavor_ir_equiv/gpu.rs::EXTRACTION_FLOORS` — nine of the ten suites; `flavor_parity` (two cases) carries no floor — and the exact zip/scan/filter ABIs in `zip_scan_and_filter_have_exact_scalar_abis`. These are structural floors, not performance measurements. Opaque computed callbacks and host-bound captures still decline — see the stage 3 checklist.
- Every kernel FORM `[GPU-KERNEL-FORM]` names compiles: named functions, inline lambdas, block-bodied lambdas, capturing closures, and recursive unannotated helpers, the last by monomorphisation (`crates/osprey-codegen/src/monofn.rs`) rather than by inlining.
- Scalar element types survive every host/device crossing: runtime lists carry an element-typed owner tag (`List#double`) exactly as buffers do, so `toGpu`/`fromGpu` round-trip floats and bools losslessly.
- Both lowerings are retained and differentially gated: `OSPREY_GPU_KERNELS` selects `extract` (default) or `inline`, any other value is a compile error, and `crates/run_test_corpus.sh` re-dispatches every `tests/core/gpu` program under the opposite lowering into `$RESULTDIR/altmode` and requires the whole observable outcome to AGREE — exit status, raw transcript bytes via `cmp`, and (under ARC) a present-and-zero leak sentinel. `test_cache_key` in `osprey-cli/src/main.rs` hashes the switch, so the two modes cannot share a cached binary.
- Differential corpus: ten suites × two flavors in `tests/core/gpu/`, **138 cases** (buffers 16, combinators 18, mlkernels 17, gamedev 21, stress 16, raster 13, scalar_contracts 7, kernel_frontier 14, flavor_parity 2, transformer 14 — `grep -c 'test('` on each Default twin; the ML twins carry the same counts under `grep -cE '^\s*test\b'`, since ML spells a case `test "name"`), covering round-trips, all ten data combinators, dot/matvec/relu/softmax/gradient descent, fixed-point particles/collision/palette work, fragment-shaped raster rendering, checked arithmetic at both sides of every i64 boundary, float accumulation ordering, million-element workloads with closed-form expected values, and — in `transformer` — the GPT-2 port's own kernels at width 4 (`gpuMatMul` exactness, k order and the no-FMA pin, the shape errors by text, the four math builtins as kernels, LayerNorm byte-exact, GELU, causal softmax and attention, embeddings, one block and the tied readout against a pure-Python oracle, and `gpuLoad`/`gpuLoadTensor` over files the program writes itself, since no lane can read a checked-in fixture). Twins emit identical IR; goldens are byte-exact — raw `cmp`, not a trimmed compare — under default/GC/ARC and wasm32. The corpus carries **no redundant type annotation**: `osprey <file> --check` reports zero `redundant-annotation` warnings for all eighteen twins, and the annotations that remain (for example `maxI(a, b: int)`, `lessF(a, b: float)`, `oobMessage(buf: GpuBuffer<int>, i)`) are the ones inference cannot replace — a comparison between two unpinned parameters has no overload resolution the way `+` now does.
- **Floors are sourced, not copied.** `GOLDEN_MIN` and `GPU_MODE_MIN` live in `crates/run_test_corpus.sh`. Quote the script, never a remembered total.
- **Dense linear algebra and model loading** (2026-10-12, forced by the GPT-2 port): `gpuMatMul(left, right, rows, inner, cols)` `[GPU-MATMUL]` is the row-major product with every element accumulated in k order from 0.0 in double and no fused multiply-add — the reference order a device lowering must reproduce — returning `Error` naming the operand whose length disagrees with the stated shape; `gpuLoad(path, offset, count)` `[GPU-BUFFER-LOAD]` reads raw little-endian binary32 words (llm.c's checkpoint layout); `gpuLoadTensor(path, name)` `[GPU-BUFFER-TENSOR]` reads one named tensor of a safetensors file, widening F64/F32/F16/BF16 exactly, with every malformed-file case an `Error` sentence. All three are one call into `compiler/runtime/gpu_host.c`, wrapped by `gpu/io.rs` through the same failure-reason channel `readFile` uses. The four float functions `sqrt`, `exp`, `ln`, `tanh` `[BUILTIN-MATH]` are total, pure, kernel-admissible by name (`gpuMap(exp)`), and lower to the LLVM intrinsics (libm `tanh`); the natural logarithm is spelled `ln` so programs keep `log` for their loggers — a reservation of `log` broke the iOS ABI fixture and a `failscompilation` fixture on first contact.

## Defects the expanded corpus exposed — now fixed

All five are fixed and pinned by `tests/core/gpu/scalar_contracts`, `tests/core/gpu/flavor_parity` and `tests/core/gpu/transformer`. They are kept here because each names a contract a device backend inherits.

1. **`fromGpu` on a float or bool buffer could not be read back** (`[GPU-BUFFER-TO-LIST]`) — FIXED. The root cause was language-wide, not GPU-specific: a runtime `List<T>` stores every element as a uniform `i64` word and nothing recorded what the word meant, so `listGet([1.5], 0)` handed back IEEE-754 bits typed as an `int` and `forEachList` printed them. Runtime list handles now carry the same element-typed owner tag buffers do (`List#double`, `crates/osprey-codegen/src/collections.rs`), `types.rs::owner_name` gives `List<T>` that tag so it survives parameters, returns and fields, and `fromGpu` copies the buffer's element type onto the list it builds.
2. **`toGpu(list-value)` lost the element tag** (`[GPU-BUFFER-FROM-LIST]`) — FIXED by the same tag: `to_gpu` reads the element type from either list representation. A worse defect sat underneath it — a list *literal* returned from a function, stored in a record field or passed to a non-inlined callee kept its flat `{ length, data }` layout while the receiver, which sees only `List<T>`, handed that header to the list runtime: `fn xs() = [1, 2, 3]` then `toGpu(xs())` gave garbage, and the float twin **segfaulted**. Every escape now normalises to the runtime layout (`crates/osprey-codegen/src/listlit.rs::escaping`).
3. **`-9223372036854775808` was accepted in Default and rejected in ML** — FIXED. The ML lexer emits the `i64::MIN` magnitude as its own token, which the parser folds under a unary minus and rejects anywhere else — the rule the Default frontend already had. The related juxtaposition defect is fixed too: a `-` spaced from what precedes it and glued to the digits that follow is a negative literal ARGUMENT (`gpuIota -3`), not subtraction, so the twins parse alike. Default's own precedence was the mirror defect — `-7 |> gpuIota()` parsed as `-(7 |> gpuIota())`, because the grammar bound `|>` tighter than unary; unary now binds tighter, matching ML.
4. **Kernel element typing was order-sensitive within one expression** (`[GPU-KERNEL-ELEM-TYPING]`) — FIXED. Call arguments are now checked against the callee's signature: non-lambda arguments are inferred and linked to their slots first, then each lambda is inferred with the parameter type those links pinned (`crates/osprey-types/src/expr.rs::positional_arg_types`). Both `fn(x, y) => t * x * y` and `fn(x, y) => x * y * t` compile, and `gpuFold(0.0, fn(a, v) => a + v)` no longer needs annotations. The NAMED context-free case (`fn plus(a, b) = a + b`) is fixed too, by the other half of plan 0022's F10: the definition records a PENDING overload instead of defaulting where no call site is in sight, and the choice is settled once, after all unification, from the operands' final types.
5. **A failed `gpuLoad` leaked its result buffer** (`[GPU-BUFFER-LOAD]`, 2026-10-12) — FIXED. `gpu_host.c` allocated the buffer before reading and returned NULL on a short read without releasing it: two live objects per failure, invisible under the default backend, silent in the C tests (linked against the non-reclaiming runtime), and caught only because `tests/core/gpu/transformer` exercises the error path twice under the ARC lane's present-and-zero leak sentinel. Every NULL-returning path in that unit now releases what it allocated (`abandoned`), `memory_golden_tests.c` links `gpu_host.c` and counts the failed load back to the floor, and the spec states that an `Error` leaves no buffer behind under any backend. The lesson for a device backend: an error path is an allocation path, and the ARC lane is the only oracle that sees it.

Both delegated cases below are closed, and `tests/core/gpu/kernel_frontier` and `tests/core/gpu/scalar_contracts` are green in both flavors under default/GC/ARC and wasm32:

- **A named context-free numeric function can serve a float slot** (F10, [the shipped scalar contract](../specs/0037-ArithmeticEffects.md#floating-point-results--float-ieee-results)). No numeric class was needed: the overload is left open and settled after unification, at the cost that one definition gets one overload (using a helper at both `int` and `float` is a type error, not a reinterpretation).
- **An empty list literal reaches codegen with its element type.** `Expr::List` carries a position, inference publishes each literal's resolved `List<T>` there (`ProgramTypes::lists`), and `toGpu([])` / `[]` tag their handle from it. The other half of that case was a language-wide inference hole: the `?:` desugaring binds its payload through an unspellable field name, and `bind_result_fields` typed anything it did not recognise as a FRESH variable, so `listGet([1, 2, 3], 0) ?: 9.5` type-checked on an `int` list and only failed in codegen. A `Success`/`Error` pattern over an unresolved discriminant now pins it to a `Result` with an open payload instead of auto-wrapping it.

## Spec statements the corpus falsified — now corrected

The corrections below have been applied to `docs/specs/0034-GPUComputation.md`; they are kept as the record of why.

- **`[GPU-KERNEL-FORM]`'s first implementation gap was stale.** A block-bodied lambda with an internal `let` works as a kernel and always did. The bullet is deleted; both flavors now exercise the case.
- **`[GPU-KERNEL-FORM]`'s second gap is now implemented, not scoped.** A recursive unannotated helper is monomorphised per instantiation (`crates/osprey-codegen/src/monofn.rs`), so the annotations are optional. Only an unresolvable *return* type still fails closed.
- **`[GPU-SCAN]` never defined its `initial` parameter** and **`[GPU-IOTA]` never defined `n <= 0`.** Both are now normative in the spec: `result[0] = combine(initial, src[0])`, and a non-positive `n` yields an empty buffer.
- **`[GPU-KERNEL-PURE]` described the kernel row as empty.** It is empty of every effect except `Arith`, which the host backend discharges through the enclosing policy; the section now says so and points at the extraction section's boundary rule.

## Design decisions carried from the research foundation

The bibliography lives in the spec's References section (`[GPU-RESEARCH]`). The *decisions* that research produced are recorded here because they shape the remaining stages. Every external fact below was re-verified against its primary source on **2026-10-12**; re-verify before any public claim.

- **Device sublanguage, not device ADTs.** Every production functional GPU language (Futhark — [Henriksen et al., PLDI 2017](https://doi.org/10.1145/3062341.3062354); Accelerate — [McDonell et al., ICFP 2013](https://doi.org/10.1145/2500365.2500595)) restricts device data to a regular, first-order scalar sublanguage; ADTs, closures and pattern matching stay in host code and at kernel boundaries. The imperative counterpart reaches the same place from the other side: Descend ([Köpcke, Steuwer, Gorlatch, PLDI 2024](https://doi.org/10.1145/3656411)) gets CUDA-parity performance with Rust-style ownership and lifetimes tracked in the type system, and Prism/Bundl ([PLDI 2026, Distinguished Paper](https://doi.org/10.1145/3808290)) puts the *granularity of thread control* into the type as "typed perspectives" so collective operations compose modularly. Osprey's ADT advantage is a host/boundary feature by design, and `[GPU-BUFFER-ELEM]` is that decision made normative.
- **Backend substrate — vendor-neutral decision checkpoint at stage 4 kickoff.** Choose a shared device representation and launch/transfer interface that can target Metal, SPIR-V, WebGPU, and optional NVIDIA-specific code generation without CUDA in the common path. Compare textual LLVM IR and a target-neutral MLIR GPU pipeline against that requirement; an `nvgpu`/`nvvm` pipeline alone does not meet it. The existing extracted flat ABI is the input to every emitter. Read Henriksen's [OpenCL/CUDA/HIP comparison](https://futhark-lang.org/publications/fproper24.pdf) for numerical and driver pitfalls; use CUDA Tile IR as optional backend research rather than the portable foundation. Record the decision and measured evidence here.
- **Effect classification is the stage-5 design.** Dex distinguishes parallelism-destroying `State` from the parallelism-preserving, monoidal `Accum` effect ([Paszke et al., ICFP 2021](https://arxiv.org/abs/2104.05372)); Xie, Johnson, Maclaurin and Paszke ([ICFP 2024](https://doi.org/10.1145/3674651)) give the formal account of which handler shapes commute with parallel evaluation — the theory closest to Osprey's handlers. The `Gpu` selection effect (stage 5) and any future accumulation effect must be designed against that work, not ad hoc.
- **Associativity does not authorize different results.** `[GPU-FOLD]` and `[GPU-SCAN]` require exact host-order results even for non-associative combines. An associativity claim alone is insufficient for floating-point reassociation; each device lowering must preserve the golden output.
- **Performance thresholds are gates, not aspirations.** Stage 4 does not promote its build flag until within 2× of a native reference on the same GPU, precision, and workload for stencil and reduction micro-benchmarks; Futhark/CUDA is one NVIDIA reference, not a prerequisite for other vendors. The measured baseline for an MLIR-based challenger is Godoy et al. ([SC Workshops 2025, WACCPD best paper](https://arxiv.org/abs/2509.21039)): Mojo is "competitive with CUDA and HIP for memory-bound kernels", with "gaps on AMD GPUs for atomic operations and for fast-math compute-bound kernels on both AMD and NVIDIA GPUs" (H100 and MI300A; seven-point stencil, BabelStream, miniBUDE, Hartree-Fock). The abstract gives no percentage; an earlier "~87%" quoted here was not in the source and is withdrawn.
- **Algorithm/schedule separation is the stage-7 shape.** The functional combinator program is the algorithm; scheduling (tiling, fusion, memory placement) becomes an optional, typed, separate layer per Halide, TVM ([Chen et al., OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/chen)) and Exo — never annotations smeared through kernel code. The tile-level authorities for what a schedule must be able to express on tensor-core hardware are CUTLASS/CuTe's layout algebra (now with a categorical foundation, [arXiv 2601.05972](https://arxiv.org/abs/2601.05972)) and ThunderKittens ([ICLR 2025](https://arxiv.org/abs/2410.20399)): 16×16 register tiles, managed shared-memory layouts, explicit asynchronous workers.
- **Autodiff is compiler-level, not library-level.** Enzyme ([Moses & Churavy, NeurIPS 2020](https://proceedings.neurips.cc/paper/2020/hash/9332c513ef44b682e9347822c2e457ac-Abstract.html); GPU kernels at [SC 2021](https://c.wsmoses.com/papers/EnzymeGPU.pdf)) differentiates LLVM IR after optimisation and was the first reverse-mode AD of GPU kernels — the natural fit for a compiler that already emits LLVM IR. The functional foundations stay Elliott (ICFP 2018), Dex, Slang.D, and the POPL 2026 account of JAX/Dex autodiff as a linear-logic calculus ([DOI 10.1145/3776654](https://doi.org/10.1145/3776654)).
- **Competitive snapshot (verified 2026-10-12):** **Mojo 1.0 shipped on 2026-08-11** and its compiler was released under Apache-2.0 with LLVM exceptions on 2026-08-18, after Qualcomm's acquisition of Modular; external compiler contributions are not yet accepted (targeted end of 2026). NVIDIA announced **CUDA Rust** (two tracks: `cuda-oxide`, early alpha, and `cutile-rs`) in September 2026 alongside the community Rust CUDA reboot. HVM2/Bend compiles higher-order functional programs to C and CUDA through interaction combinators — the other functional-on-GPU route, with none of Osprey's static guarantees. Typed GPU programming has active venue appetite (Prism/Bundl at PLDI 2026; Kuiper at ARRAY 2025 — dependent types and concurrent separation logic extracting to CUDA; the POPL 2026 AD paper) — publishing the device sublanguage's type-and-effect rules is a credibility play worth its own milestone.

## Where the design already commits to the right shape — and where it must change

Where the current design already commits to the right shape:

- **Purity is proven, not promised.** `[GPU-KERNEL-PURE]` is discharged by the effect checker and fails closed. Every offload decision downstream rests on it, and no competitor with a library-shaped GPU surface can make it.
- **The element restriction is the device sublanguage.** `[GPU-BUFFER-ELEM]` is the Futhark/Accelerate discipline made normative before any device code exists, so no accepted program will have to be un-accepted later.
- **The buffer layout is already the transfer layout.** Dense, unboxed, contiguous — a device copy is a `memcpy`, not a marshalling pass.
- **The extracted ABI is the emitter's input.** Uniforms then element slots, scalar return, no environment pointer: a PTX/AIR/SPIR-V emitter walks that signature directly.
- **The host backend is the oracle.** Every backend is held byte-for-byte to it, and the `extract`/`inline` differential proves the harness can actually hold two code generators to one golden.

Where it will have to change — name these before promising anything:

- **One dimension.** Every combinator is rank-1 over a flat buffer. Real GPU work is `(x, y, z)` blocks and grids; a matrix today is a flat buffer plus an index kernel (`mlkernels`'s `matVec` literally does this). Multi-dimensional index spaces are a **surface change**, not a backend change, and the longer the corpus encodes flat indexing the more expensive it gets.
- **Transfer is invisible.** `toGpu`/`fromGpu` are a copy on the host today. Once a device exists they become the host↔device boundary, and a program that calls them in a loop is a program that is memory-bound by accident. Making the cost visible — in the type, in an effect, or in a diagnostic — is a design decision that has not been made.
- **No memory hierarchy.** Shared/local memory, tiling and coalescing are what separates a working kernel from a fast one. Stage 7's schedule layer is the intended home; nothing about the current surface expresses it.
- **No fusion between combinators.** Only `toGpu` fuses its iterator source; every other combinator allocates its result and runs its own loop. A transformer layer written today is a dozen buffers per token.
- **Reductions are semantically host-ordered.** `[GPU-FOLD]` and `[GPU-SCAN]` require the host's left-to-right result, pinned by `horner`, `subI`, and the float-ordering case. A device backend may reassociate only when it preserves the exact result; otherwise it must preserve the original order or use a sequential fallback. Keep the existing goldens and assertions.
- **Kernels that decline extraction have no device story.** Opaque computed closure cells and host-bound bodies lack a device-ready ABI. A device backend must reject the remaining unsupported shapes with a diagnostic naming the kernel, never silently offload.

## Reference application — GPT-2 from `llm.c`

The yardstick for every one of the gaps above is a real model, and the right one is Karpathy's [`llm.c`](https://github.com/karpathy/llm.c): GPT-2 pretraining in plain C and CUDA, with a ~1 000-line fp32 CPU reference (`train_gpt2.c`), the CUDA mainline (`train_gpt2.cu`), and a `dev/cuda` ladder of kernels from naive to tuned for every operation a transformer needs (matmul, layernorm, GELU, softmax, attention, residual, Adam). It is the standard "basic LLM that leverages GPUs" and it comes with its own reference outputs. The existing `mlkernels` suite (dot, matvec, relu, softmax, gradient descent) is the seed of this port, not a substitute for it.

**Status: half A inference landed 2026-10-12; backward pass not started; half B blocked on stage 4.**

- **Half A — host parity.** `examples/gpt2/gpt2.osp` (one file, under the cap) loads the weights Hugging Face publishes (`model.safetensors`, `merges.txt` from `openai-community/gpt2` — llm.c's own `.bin` starter pack is gated behind a Hugging Face login, so the public interchange format became the loader's target and `gpuLoad` covers the raw layout too), rebuilds the byte-level BPE tokenizer from the merge list alone (merge *i* is token 256 + *i*, so `vocab.json` is never read), runs the twelve blocks as `gpuIota |> gpuMap` kernels plus `gpuMatMul`, and samples greedily. The oracle is `examples/gpt2/reference.py`, a pure-Python forward pass over the same files with the same left-to-right accumulation order. Result: identical token ids on every prompt tried (ASCII, contractions, multi-space runs, UTF-8), and every greedy continuation compared identical (all 20 tokens of the default prompt; the two of `Hello, I'm a language model,`). Measured (AMD Ryzen 9 3900X, Linux 6.18 under WSL2, release build): load 9.3 s; about 1.25 s per token at 5–25 tokens of context without a KV cache; 20 tokens in 34 s at a 10.0 GB peak under the default (non-reclaiming) backend, 42 s at 1.3 GB under ARC; the Python reference takes 16 min 25 s for the same 20 tokens. `make gpt2 PROMPT="…" TOKENS=n` downloads and runs. The backward pass and an optimiser step are the remaining half-A items; they need a loss (`ln` landed for it) and the same tolerance discipline.
- **What the port forced into the language**, each with spec, tests and docs: `[GPU-MATMUL]`, `[GPU-BUFFER-LOAD]`, `[GPU-BUFFER-TENSOR]`, `[BUILTIN-MATH]` (above), and two codegen defects that any list-building program could hit — `fold([], fn(acc, i) => listAppend(acc, x))` segfaulted on its second iteration because the seed's flat-literal representation was re-imposed on the loop-carried runtime list (`iter.rs::acc_init` now converts the seed once, at the escape), and `listGet` on a `let`-bound `lines()` result copied the whole string list per read (50 000 lines × 5 000 reads: 8.8 s and 6.9 GB; `stmt/bindings.rs` now settles a string list to the runtime layout once at the binding: 0.08 s). The second fix exposed a third: `join` read only the flat `osp_string_list` layout and segfaulted on any runtime list (`listAppend`, `toList`, a fold result, and now a bound `words()`); `strings.rs::join` converts to the runtime layout and calls `osp_string_join_list`, which borrows the words into a flat view so both layouts share one join.
- **What the port says about the four surface gaps.** Rank-1 indexing: every kernel in the model is flat index arithmetic — `intDiv(i, width)`, `i % width`, `(h * t + r) * t + c` — and the attention kernels index a `[heads, t, t]` tensor by hand; a rank-2/rank-3 index space is the single largest readability win available. No fusion: one block allocates nineteen buffers per step (two LayerNorm statistics pairs, qkv, five attention intermediates, two residuals, the MLP hidden state and six bias passes); every `linear` is a product followed by a separate bias gather, which a fused `gpuMatMul` epilogue or combinator fusion would delete. Host-ordered reductions: harmless here — the per-row folds are exactly the sequential order the oracle uses, which is why the token ids agree. Invisible transfer: not observable on the host backend; the model's hot loop recomputes the whole sequence each step, so a device backend without a KV cache would move every layer's activations every token.
- **Half B — device parity, the stage 4 gate.** The same Osprey program, unchanged, against a native GPT-2 reference on the same GPU and at matching precision. Use `llm.c`'s CUDA path as the NVIDIA comparison and an equivalent Metal, Vulkan, or WebGPU reference on other devices; CUDA is a benchmark option, not an Osprey dependency. The 2× threshold that gates the stage 4 build flag is measured here, not only on micro-benchmarks.

## Remaining stages

4. **Portable device execution.** A shared device representation and launch/transfer contract, with a platform adapter that executes the GPT-2 example on the available GPU without CUDA. Metal on Apple hardware and SPIR-V or another platform compute API on AMD/Intel/NVIDIA must share the same Osprey surface. Optional CUDA support plugs into this contract. Keep experimental adapters behind build flags until their device parity and 2× benchmark gates pass.
5. **Effect-selected execution.** A static effect whose handler chooses the execution strategy per lexical region; `gpuDevice()` reports the handler's choice; a test handler pins `"host"` so CI is deterministic with no GPU attached. This is the construct competitors bolt on as library calls — the headline language feature. Landed 2026-10-13 as the program's own `Tensor<B>` effect rather than a built-in `Gpu` effect: GPT-2 is written once against it and `onLists`/`onGpu` are two `handle static` interpretations (below).
6. **Expand backend coverage and graphics convergence.** Vendor independence is mandatory from stage 4; this stage expands platform coverage rather than introducing portability after a CUDA implementation. Metal (macOS CI can actually execute it; MSL is at specification 4.1 as of 2026-06-04) and WebGPU/WGSL beside the existing wasm target (WebGPU is a W3C Candidate Recommendation with drafts through 2026; Futhark has shipped and iterated a WebGPU backend, 2024–2025, which is the closest prior art for a functional array language on WGSL). Plan 0025's convergence point is here.
7. **Autodiff and schedules.** Differentiable kernels (Enzyme-style compiler AD over the emitted IR; Elliott's categorical core; Dex's parallelism-preserving accumulation; Slang.D's differentiable type discipline) and the optional schedule layer.

Stages ratchet: each keeps `make ci` green and the differential harness byte-exact, and later stages must not change the meaning of programs accepted by earlier stages (`[GPU-ROADMAP]`).

Landmines previous sessions hit:

- The device backends have no signed 64-bit division: `long / long` compiled by Metal's backend crashed it (`XPC_ERROR_CONNECTION_INTERRUPTED`) and OpenCL kernel creation failed with status -48. Every checked helper divides unsigned magnitudes. Never use a Metal device across `fork`; test aborts with mock adapters.
- A kernel's captures decide its device form: a record (`w.wte` inside the body), a list (`listGet(ids, …)`) or a string keeps it on the host. Pass the buffers and scalars themselves (`embedRow(wte, wpe, token, p)`, `idTensor(ids)` compared as floats), and read the reason the launch site records when a device run aborts.
- Directly recursive generic helpers are emitted by `monofn.rs`, including buffer parameters, rather than recursively inlined. An unresolved return type still fails closed; mutual generic recursion remains subject to the re-entry guard. Do not reintroduce parameter annotations where the call site supplies the type.
- Twins must emit identical IR (`cargo test -p osprey-cli --test cross_flavor_ir_equiv`), so a construct only one flavor's parser accepts cannot enter the corpus.
- Goldens are byte-exact under default/GC/ARC **and** wasm32. Wasm goldens run under `make wasm`, not `make ci` — run both. `make wasm` also *builds* `libosprey_runtime_wasm.a`; without it every wasm golden fails at once. The tell is the harness's `TEST_CORPUS_SKIPPED=… TARGET=wasm32` line: it must equal the non-comment entry count of `tests/WASM_UNPORTABLE.txt` (the manifest is the source; do not copy the number here), and 0 means the wasm runtime archive did not build.
- `GOLDEN_MIN` counts *programs*, not test cases — adding a `test(...)` to an existing suite does not move it. Never lower it. `GPU_MODE_MIN` counts the `tests/core/gpu` programs re-run under the opposite kernel lowering; a tenth suite raises it by two. Both live in `crates/run_test_corpus.sh`.
- **A new kernel lowering must be cache-keyed.** `test_cache_key` hashes `OSPREY_GPU_KERNELS`; without that the harness compares one cached binary to itself and the differential silently passes forever. Falsify any new mode gate by breaking it on purpose once and watching it fail.
- The deslop duplication ceiling is defined in `.deslop.toml`. A new combinator must sit on the existing chassis — `kernel_of` for its kernel, `map_into` if it produces a buffer per element, `reduction` if it carries an accumulator, `kernel_loop` underneath — and any new lifted-call helper must reuse `closure.rs` rather than restating it. The element rule is `gpu::is_scalar`; do not restate its three-way match anywhere in GPU code. (`llty::scalar_spelling`'s four-way match, which also admits `Str`, is the owner-tag spelling table, not the element rule.)
- `gpu.rs` and `gpu_kernel.rs` are each within a hundred lines of the 500-LOC cap. The next addition to either goes in a new module beside `gpu/buffer.rs`, not at the bottom of the file.
- Float `/` returns `float`; a nonliteral divisor requires an enclosing runtime `Arith.divideByZero` policy on the host backend ([spec 0037](../specs/0037-ArithmeticEffects.md)). ML twins: no braces in constructor patterns (`Success value`), lambdas are `\x => …`, parenthesize match-arm and pipe continuations, and **parenthesize a negative literal argument** (`gpuIota (-4)`) or juxtaposition reads it as subtraction.
- A builtin passed by name as a callback needs a value form in `expr.rs::call_builtin_with_values`, or it emits `call @name` to a symbol that is never defined and fails at *link* time with no source location.
- A line opening with `(` starts a NEW statement ([LEX-STATEMENT-BREAK](../specs/0002-LexicalStructure.md#the-rule-lex-statement-break)). A callee and its argument list must still share one line.
- Lifted host kernels and materialized source lambdas emit their own `DISubprogram`, parameters and captured values; see [plan 0012](0012-osprey-debugger.md).
- Annotations in the corpus are defects unless the compiler keeps them: run `osprey <file> --check` and strip every `redundant-annotation` it names, in both twins, then prove the golden unchanged with `cmp`.
- `/` on two ints is FLOAT division ([spec 0037](../specs/0037-ArithmeticEffects.md)); an index computation wants `intDiv`. Float literals have no exponent form (`1.0e308` is a syntax error) — seed a float fold from an element, not from a sentinel. `toString` has no `List<T>` form; render a list with a `fold` over `range`. `print` is `puts`: a segfaulting program loses everything still in the stdout buffer, so bisect a crash with `stdbuf -o0` on the compiled binary, not by reading what printed.
- The default memory backend reclaims nothing. A program that allocates per iteration (GPT-2: nineteen buffers per block per token) grows without bound — 10 GB for 20 tokens — and must be run under `--memory=arc`, which `make gpt2` does. Measure memory under the backend you will ship with.
- A builtin name is reserved against user definitions. Adding one is a breaking change for every program that already uses the identifier (`log` was in two fixtures); name a new builtin so it collides with nothing in the tree and nothing a downstream logger would want.

- [x] Shared dispatch contract (`gpu_device.h`: `OspreyGpuDispatch`, `osprey_gpu_launch`, `osprey_gpu_declined`), direct Metal/OpenCL adapters with one library/program per process and one pipeline per kernel name (`gpu_metal.m`, `gpu_opencl.c`), and one device dialect (`gpu_f64.metal`, `gpu_math64.metal` with correctly rounded `exp`/`ln`/`tanh`, `gpu_device_lib.metal` with the checked integer helpers and the fault word); no CUDA dependency, no CPU fallback after GPU selection, `gpu_shader_tests.c` holds the dialect to the host's IEEE results as C.
- [ ] Device-resident buffers and kernel-to-kernel fusion: every launch still uploads its inputs and copies its result back, and `gpuIota`/`toGpu`/`fromGpu`/the loaders run on the host. Capability negotiation beyond the two adapters.
- [ ] `gpuScan` and `gpuFilter` device forms (a sequential scan is the fold shape; compaction needs a kept-count channel in the launch contract).
- [ ] **Transcendental determinism decision.** The device's `exp`/`ln`/`tanh` are correctly rounded and a host libm is not, so a value through one can differ in its last digit between the host and the device. Adopting the device library on the host too would make every backend bit-exact and every platform agree ([FLOAT-IEEE-RESULTS] tolerates libm differences today), at a [BUILTIN-MATH] semantics change and a CPU cost to measure.
- [x] GPT-2 inference and training run every kernel and every product on the selected device by default (`GPU=auto`); `GPU=host` remains the oracle. Failed tensor loading, a failed dispatch, a kernel fault and a kernel without a device form abort naming themselves instead of fabricating a result or silently running on the CPU.
- [ ] CI with and without GPUs: adapter code compiles on its platforms; hardware lanes verify completed device dispatch and host parity. Cover Apple, AMD, Intel, and NVIDIA as adapters land. A CUDA-only lane cannot close portable GPU delivery.
- [x] **Decline-to-offload diagnostic** (2026-10-15): a launch site whose kernel has no device form calls `osprey_gpu_declined` with the reason (the capture that blocks it, by name and kind); the host runs the loop, a selected device aborts naming it.
- [x] **Non-associative reduction decision** (2026-10-15): a device `gpuFold` is one thread folding in element order, so [GPU-FOLD]'s host-order result is preserved exactly; a parallel reduction is admissible only where it provably preserves the same result.
- [ ] Benchmark gate: within 2× of native references on the same GPU and at matching precision for stencil + reduction micro-benchmarks AND GPT-2 half B before the flag is promoted; record numbers in `benchmarks/`.

### Stage 5 — effect-selected execution

- [x] Purity interaction: kernels stay pure; a callback an arm forwards to `gpuMap`/`gpuZipWith`/`gpuFold` is held to [GPU-KERNEL-PURE] and rejected by name when it performs a runtime effect (`examples/failscompilation/staged_forwarded_kernel_dynamic.ospo` and its ML twin).
