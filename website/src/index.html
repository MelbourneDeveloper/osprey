01 / A different way to connect

Your logic stays.
The implementation changes.

Your editor needs to save a draft. The save function requests storage and decides what to show when it succeeds or fails.

The disk handler writes the file. The offline handler simulates failure without touching storage. Swap the handler around the work; no storage parameter needs to pass through every helper.

Understand algebraic effects ↗
  1. 01

    Declare the need.

    effect defines an operation and its types. perform asks for it.

  2. 02

    Choose the behavior.

    A reusable handler supplies the implementation while your function runs.

  3. 03

    Let the compiler check the boundary.

    Missing handlers and incompatible operation types are compile errors.

04 / A model on the surface

The trained GPT-2.
Written once. Run on the GPU.

gpuLoadTensor reads the published weights. The model performs a static Tensor effect. One handler answers it with plain lists. The other answers every operation with a GPU-surface kernel or a gpuMatMul product, and Metal or OpenCL executes them.

On the CPU every number matches an independent pure-Python reference exactly, token ids and gradients alike. On an Apple M4 Max a training step runs about three times faster on the GPU than on the CPU. The text is the same, and the numbers agree to twelve digits.

Read how it was ported ↗
examples/gpt2/model/model.ospLayerNorm
fn normalised(x, means, variances, g, b, i) = {
    let r = intDiv(i, width)
    let c = i % width
    (at(x, i) - at(means, r)) / sqrt(at(variances, r) + epsilon) * at(g, c) + at(b, c)
}

export fn layerNorm(x, t, g, b) = {
    let means = rowMeans(x, t)
    let variances = rowVariances(x, t, means)
    perform Backends::Tensor.build(t * width, fn(i) => normalised(x, means, variances, g, b, i))
}
